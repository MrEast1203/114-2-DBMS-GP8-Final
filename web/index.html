在單一 PostgreSQL 內,把語義 + 精準 + 圖三種搜尋編排到最快又最準

PostgreSQL 的 planner 看不到三條搜尋管道彼此的成本。本專案用一層 Rust 編排器,做了四個版本的查詢計畫,證明:光重排執行順序沒用,真正的關鍵是把「圖過濾」push-down 進 ranker SQL,再 chain 一道 BM25 → pgvector。這個互動頁面把全部量測結果視覺化。

§01 · Architecture

三個成本各自獨立的引擎,合在一個資料庫裡

語料是 36 740 篇 OpenAlex 論文 abstract。三個搜尋引擎住在同一個 PostgreSQL 裡,但 query planner 無法跨引擎估算成本——於是我們在 SQL 之上加一層 Rust 編排器來統籌。

▼   三路結果交給   ▼
Orchestrator researchdb-bench · Rust + sqlx selectivity 估算 · cost annotation · graph push-down · RRF 融合 (k=60)
編排器不在 PostgreSQL 裡面,而是在應用層。它決定每個引擎的執行順序、要不要把圖過濾集合當白名單塞進 ranker 的 WHERE id = ANY($filter),最後用 Reciprocal Rank Fusion 把多路排名融成一份 top-10。

§05 · Anatomy of the trick

Push-down 到底做了什麼

以 Q6(語義 ∩ 精準)為例。naive 讓兩個 ranker 各自排完整個 corpus 再交集;v3 把 BM25 的 top-N 當白名單 chain 進 pgvector,讓最貴的向量搜尋只看最小的候選集。

naive(圖當 RRF 後的 post-filter)對上 v2(圖當 pre-filter push-down 進 ranker SQL)已經回答了:把圖移出排名階段,平均 NDCG@10 從 0.772 拉到 0.917(+0.145)。v3 沿用 v2 的選擇——圖只當過濾,永遠不進 RRF。
